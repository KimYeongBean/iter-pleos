# 0003. 기록 저장소를 SQLCipher로 암호화하고 키는 Android Keystore로 보호한다

- 상태: 제안
- 날짜: 2026-11-13
- 관련 이슈: #126
- 영향받는 모듈: `:vehicle` (기록 저장소), `:app` (기록 저장소를 여는 쪽, APK 크기)
- 결정한 사람: (리뷰 후 기입)

## 맥락
기록 저장소(Room, `records.db`)에는 초 단위 시각, 속도, 차량 신호, 위도·경도가 평문으로 저장되어 있었다. 위치만으로도 집과 직장, 이동 패턴이 드러난다.

Pleos 앱 보안 가이드(app-security-guide)는 "기기에 저장하는 민감정보는 저장 위치와 관계없이 암호화"하고, SQLite 데이터베이스에도 "앱 수준의 암호화를 적용"하며, 키는 "Android Keystore 등"으로 보호하라고 요구한다. 지키지 않으면 "앱 심사를 통과하지 못할 수 있다"고 명시되어 있다.

검토한 선택지:
- **SQLCipher로 파일 전체 암호화 (채택)**: 표, 색인, 앞으로 추가될 열까지 모두 암호화된다. 라이브러리가 추가되어 APK가 커진다.
- 민감한 열(위도·경도)만 Keystore 키로 암호화: 라이브러리는 필요 없지만, 열이 늘어날 때 빠뜨리기 쉽고 시각·속도는 평문으로 남는다.

## 결정
- `records.db` 전체를 SQLCipher(`net.zetetic:sqlcipher-android`)로 암호화하고 Room에 `SupportOpenHelperFactory`를 연결한다.
- 암호(passphrase)는 설치마다 한 번 무작위로 만든다(32바이트). Android Keystore의 AES-256-GCM 키로 감싼 값만 SharedPreferences에 저장한다. 평문 암호는 디스크에 남지 않는다.
- 암호화 이전의 평문 DB는 처음 열 때 그 자리에서 암호화한다(`sqlcipher_export`). 암호화된 사본이 열리는지 확인한 뒤에 바꿔치기하므로 도중에 실패해도 기록이 남는다. 실패하면 이번 실행만 평문으로 열고 다음 실행 때 다시 시도한다.
- Keystore가 초기화되는 등으로 암호를 풀 수 없으면, 읽을 수 없는 DB를 지우고 새로 시작한다. 앱이 계속 죽는 것보다 낫다고 판단했다.
- JVM 단위 테스트(Robolectric)에서는 SQLCipher 네이티브 라이브러리를 불러올 수 없어서 평문 DB를 쓴다(`Build.FINGERPRINT == "robolectric"`일 때만).

## 결과
- 좋아지는 점: 기기에서 DB 파일을 꺼내도 내용을 읽을 수 없다. 보안 가이드의 암호화·키 관리 요구를 충족한다.
- 감수하는 점:
  - debug APK 기준 크기가 늘어난다 (ABI별 SQLCipher 네이티브 라이브러리).
  - 처음 열 때 Keystore로 암호를 푸는 시간이 든다. Pleos 에뮬레이터에서 약 150ms였고, 평문 DB를 처음 변환할 때는 샘플 24,149개 기준 약 370ms였다. 기록 저장소는 지금 메인 스레드에서 처음 열린다.
  - Keystore를 잃으면 기록도 잃는다 (백업이 꺼져 있으므로 복구 수단 없음).
- `:vehicle`: `RecordStore.open`의 시그니처는 그대로다. `docs/interfaces.md`는 바꾸지 않는다.
- `:app`: 바꿀 코드는 없다. 기록 저장소를 메인 스레드 밖에서 처음 열도록 옮기는 것은 별도로 검토한다.
